# Часть 2. Экономическая фаза и завершение хода

## 2.1. Место в последовательности `applyOrders`

Полная последовательность фаз внутри `applyOrders(state, orders)`:

1. **Подготовка.** `tmpr_owner = owner` для всех тайлов. Копия `state` в рабочее состояние.
2. **Экономическая фаза.** Применение `Order1`, `Order4`, `Order3`. Применение `Order5` (задание `retreat_province`).
3. **Этап перемещения** (Часть 3).
4. **Основной бой** (Часть 4).
5. **Завершение хода** (эта часть, 2.6).
6. **Проверка win condition** (эта часть, 2.7).

Всё, что описано в этой части, относится к шагам 2, 5, 6.

## 2.2. Порядок применения экономических приказов

Фиксированный порядок (чтобы поведение при нехватке денег было детерминированным):

1. Все `Order1`, отсортированные по `owner.id` возрастанию.
2. Все `Order4`, отсортированные по `owner.id` возрастанию.
3. Все `Order3`, отсортированные по (`owner.id`, `recipient.id`) возрастанию.

Внутри одного типа порядок фиксирован. Между типами порядок фиксирован. Это убирает недетерминизм, если клиент пришлёт приказы в произвольном порядке.

**Проверка средств.** Клиент обязан гарантировать, что суммарные траты не превышают `treasury`. Но модуль не полагается на это. Если `cost > treasury` на момент применения приказа:

- приказ **игнорируется целиком**;
- поля `treasury`, `investments`, `capital.army.infantry/cannons`, `recipient.gifts` не меняются.

Это простой, детерминированный fallback. Альтернатива (обрезать до остатка) хуже тем, что для `Order4` неясно, что именно обрезать — пушки или пехоту.

## 2.3. `Order1` — инвестиции

```text
apply_Order1(state, order):
    c = order.owner
    cost = order.investments
    if cost > c.treasury:
        return                          // игнорируем целиком
    for t in order.tiles:
        t.investments += cost
    c.treasury -= cost
```

Важно: `cost` списывается из казны **один раз**, независимо от количества тайлов в `order.tiles`. Каждый тайл получает полную сумму `cost`. Это контринтуитивно, но так задумано.

`Order1.owner` не обязан совпадать с владельцем тайлов в `order.tiles`. То есть страна X может инвестировать в тайлы, принадлежащие Y.

Инвариант `tile.investments` не обнуляется между приказами — он накапливается. Обнуляется только в конце хода.

## 2.4. `Order4` — создание юнитов в столице

```text
apply_Order4(state, order):
    c = order.owner
    inf = order.infantry
    can = order.cannons
    cost = (inf * 1 + can * 3) * 1000       // scale 1000
    if cost > c.treasury:
        return                              // игнорируем целиком
    c.capital.defenders.army.infantry += inf
    c.capital.defenders.army.cannons  += can
    c.treasury -= cost
```

Стоимости: 1 за пехоту, 3 за пушку (в игровых единицах). `treasury` в scale 1000, поэтому умножаем на 1000.

Новые юниты добавляются прямо в существующий гарнизон столицы. `origin` этой армии — уже `capital` (не меняем). `losed*` не трогаем.

## 2.5. `Order3` — подарки

```text
apply_Order3(state, order):
    c = order.owner
    r = order.recipient
    amount = order.gift
    if amount > c.treasury:
        return
    r.gifts += amount
    c.treasury -= amount
```

`Order3` не имеет смысла для `c == r` (перевод самому себе), но модуль это не запрещает — просто `treasury -= amount`, `gifts += amount`, нетто-эффект `treasury - amount, gifts + amount`. Пусть это будет валидным поведением (клиент не должен присылать такой приказ, но модуль его не ломает).

## 2.6. `Order5` — задание отступления

```text
apply_Order5(state, order):
    order.tile.retreat_province[order.owner.id] = order.retreat_province
```

`order.tile` — любой тайл. `order.retreat_province` — любой тайл (не обязательно соседний, не обязательно свой). `null` означает «уничтожение».

Если от одной страны пришло несколько `Order5` для одного тайла, применяем **последний в порядке возрастания `owner.id`**? Нет — это недетерминировано, потому что порядок прихода не фиксирован. Правильнее: приказы одного типа от одной страны для одного тайла **сливаются в один**, если совпадают `tile` и `owner`. Если у них разные `retreat_province` — приказ считается невалидным и игнорируется. Если хотя бы один приказ валиден и все валидные приказы дают один результат — применяем его.

На практике клиент должен присылать не более одного `Order5` на пару (`owner`, `tile`). Модуль просто фиксирует: **не более одного**, иначе приказ игнорируется целиком.

## 2.7. Расчёт `economy` после инвестиций

Применяется один раз для всех тайлов, после того как все `Order1` применены.

```text
apply_investments(state):
    N = state.tiles.length
    for t in state.tiles:
        e = t.economy                       // scale 1000
        inv = t.investments                 // scale 1000
        num = N * e + 4 * inv
        den = N * e + 2 * inv
        t.economy = floor(e * num / den)
```

Эквивалентно формуле

```
economy_new = economy * (2 - 1 / (1 + investments / (N/2 * economy)))
```

но в целых числах. Проверка: если `inv = 0`, то `num = den = N*e`, результат `floor(e) = e`, экономика не меняется. Если `inv > 0`, множитель > 1, экономика растёт.

`N * e` при масштабе 1000: например, `N = 100`, `e = 10^6` → `10^8`. `e * num` → `10^14`, безопасно в `number`.

Значения `tile.investments` при этом не обнуляются — они сбрасываются в конце хода вместе с другими транзиентными полями.

## 2.8. Завершение хода

Порядок строгий.

### Шаг 1. Применить накопленные потери к `origin`

Для каждой армии в игре (в `Tile.defenders.army`, плюс временно — в `Tile.conquerors`/`retreated`, если они ещё не сброшены):

```text
for army in all_armies(state):
    o = army.origin
    o.defenders.army.infantry = max(0, o.defenders.army.infantry - army.losedinfantry)
    o.defenders.army.cannons  = max(0, o.defenders.army.cannons  - army.losedcannons)
    army.losedinfantry = 0
    army.losedcannons  = 0
```

На практике к этому моменту `Tile.conquerors` и `Tile.retreated` уже пусты (сбрасываются в Части 4), а `army.losed*` есть только у армий, находящихся в `defenders.army` или в `defenders.support`. Support-армии тоже нужно обработать: их `losed*` идут в их `origin`, но при этом они **не** в `Tile.defenders.support` после боя (список очищается). Значит, `sync` надо делать **до** очистки `defenders.support`.

Правильный порядок — sync первый, очистка транзиентных полей вторым.

### Шаг 2. Пересчитать `Country.tiles`

```text
for c in countries:
    c.tiles = [t for t in state.tiles if t.owner == c]
    sort c.tiles by t.id asc
```

### Шаг 3. Пересчитать `Country.income`

```text
for c in countries:
    c.income = sum(t.economy for t in c.tiles)
```

### Шаг 4. Обновить `Country.treasury`

```text
for c in countries:
    c.treasury = floor(c.treasury * 800 / 1000) + c.gifts + c.income
    c.gifts = 0
```

«Сгорание» (20%) применяется к `treasury` до прибавления `gifts` и `income`.

### Шаг 5. Очистить транзиентные поля

```text
for t in state.tiles:
    t.investments = 0
    t.tmpr_owner = t.owner
    t.defenders.support = []
    t.retreated = null
    t.conquerors = []
for army in all_armies(state):
    army.retreat = 0
```

`tile.retreat_province` **не** сбрасывается — это постоянное поле.

### Шаг 6. Увеличить `turn`

```text
state.turn += 1
```

## 2.9. Win condition

Проверяется после всех расчётов, в конце `applyOrders`, на финальном состоянии.

```text
check_win(state) -> bool:
    world_income = sum(c.income for c in state.countries)
    max_income = max(c.income for c in state.countries)
    return max_income * 2 >= world_income
```

Если `check_win(state)` истинно — `applyOrders` **не бросает исключение**, а возвращает `{ state, gameEnded: true, winners: [...] }`. Ранжирование стран по `income` на момент окончания:

```text
ranking = countries sorted by income desc, tie-break by id asc
```

Первое место — максимум, последнее — минимум. `applyOrders` возвращает `ranking` вместе с `state`, чтобы UI мог показать таблицу.

## 2.10. Возвращаемое значение `applyOrders`

```text
applyOrders(state, orders) -> ApplyResult

ApplyResult {
    state: GameState
    gameEnded: boolean
    ranking: Country[] | null      // null если игра не закончилась
}
```

`state` — новое, не мутирует входной. `ranking` заполнен только при `gameEnded == true`.

## 2.11. Примеры

### Пример 1: инвестиции

Старт:

```text
C0.treasury = 10_000        // scale 1000 → 10 игровых единиц
T0.economy = 1_000_000      // scale 1000 → 1000 игровых
T1.economy = 1_000_000
N = 2
```

Приказ:

```text
Order1 { owner: C0, investments: 5_000, tiles: [T0, T1] }
```

Применение:

- `C0.treasury = 10_000 - 5_000 = 5_000`.
- `T0.investments = 5_000`, `T1.investments = 5_000`.

Расчёт `economy`:

```text
N = 2
Для T0: num = 2 * 1_000_000 + 4 * 5_000 = 2_020_000
        den = 2 * 1_000_000 + 2 * 5_000 = 2_010_000
        new_e = floor(1_000_000 * 2_020_000 / 2_010_000) = floor(1_004_975) = 1_004_975
```

Экономика выросла примерно на 0.5% — потому что формула нелинейная, и `investments` малы относительно `N/2 * economy = 1_000_000`.

Если `investments = 1_000_000` (игровая 1000):

```text
num = 2_000_000 + 4_000_000 = 6_000_000
den = 2_000_000 + 2_000_000 = 4_000_000
new_e = floor(1_000_000 * 6_000_000 / 4_000_000) = floor(1_500_000) = 1_500_000
```

Рост в 1.5 раза.

### Пример 2: нехватка денег

```text
C0.treasury = 1_000
Order4 { owner: C0, infantry: 5, cannons: 2 }
```

`cost = (5*1 + 2*3) * 1000 = 11_000`. `11_000 > 1_000` → приказ игнорируется. `treasury` остаётся `1_000`, юниты не добавляются.

### Пример 3: подарок и сгорание

```text
C0.treasury = 10_000
C1.treasury = 20_000
C0.income = 30_000
C1.income = 10_000
C0.gifts = 5_000       // пришло от C1
C1.gifts = 0
```

Конец хода:

```text
C0.treasury = floor(10_000 * 800 / 1000) + 5_000 + 30_000 = 8_000 + 5_000 + 30_000 = 43_000
C1.treasury = floor(20_000 * 800 / 1000) + 0      + 10_000 = 16_000 + 10_000       = 26_000
```

### Пример 4: win condition

```text
C0.income = 100_000
C1.income = 50_000
C2.income = 50_000
```

`world_income = 200_000`, `max_income = 100_000`. `100_000 * 2 = 200_000 >= 200_000` → истинно. Игра заканчивается, `ranking = [C0, C1, C2]` (C1 и C2 равны, tie-break по id).

Если `C0.income = 99_999` — игра не заканчивается.




1. Order3 с owner == recipient — приказ невалиден, игнорируется целиком. Ни treasury, ни gifts не меняются.
2. Order5 валиден, только если retreat_province == null или retreat_province ∈ order.tile.neighbours. Иначе приказ игнорируется целиком.
3. ApplyResult.ranking возвращается всегда, не только при gameEnded == true. Сортировка по income desc, tie-break по Country.id asc.
4. applyOrders всегда возвращает state в чистом виде, включая случай gameEnded == true (транзиентные поля сброшены, turn увеличен).
